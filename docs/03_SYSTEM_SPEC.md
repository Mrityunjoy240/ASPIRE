## 2. The Attendance Engine

The Attendance Engine is responsible for calculating current attendance, projecting future attendance, and emitting risk signals. It relies only on VERIFIED attendance records.

### 2.1 Current Attendance Calculation
`Attendance % = (Classes Attended / Classes Conducted) * 100`

**Rules:**
- Rounded to 2 decimal places.
- Only counts classes up to the current date.
- Does NOT include scheduled future classes.
- If `Classes Conducted == 0`, Attendance % is `null` (not 0, not 100).

### 2.2 What-If Projection (Recovery Calculation)
This function determines how many consecutive future classes a student must attend to reach the configured `ese_eligibility_threshold`.

**Function:** `calculate_required_classes(attended, conducted, target_threshold)`
**Logic:**
```
required_classes = 0
current_attended = attended
current_conducted = conducted

WHILE (current_attended / current_conducted) * 100 < target_threshold:
    required_classes += 1
    current_attended += 1
    current_conducted += 1

RETURN required_classes
```

### 2.3 Attendance Risk Emitter
Runs after every attendance update for a student.

**Rules:**
- IF Attendance % < `ese_eligibility_threshold` AND Attendance % >= `condonation_minimum`:
  Emit Event: `ATTENDANCE_RISK_WARNING` (Payload: subject, current %, required classes)
- IF Attendance % < `condonation_minimum`:
  Emit Event: `ATTENDANCE_RISK_CRITICAL` (Payload: subject, current %)

## 3. The Assessment Engine (CIA/PCIA)

The Assessment Engine tracks continuous evaluation marks.
*(Note: Waiting on OQ-06 for exact BCREC autonomous CIA/PCIA weightings).*

### 3.1 Assessment State
For every subject, the engine maintains:
- `pending_assessments`: Array of assessments where `deadline > now` and `submitted == false`.
- `missing_assessments`: Array of assessments where `deadline < now` and `submitted == false`.
- `completed_assessments`: Array of assessments with a numeric score or official `0`.

### 3.2 Assessment Risk Emitter
Runs daily and upon new assessment data entry.

**Rules:**
- IF a student has > 0 `missing_assessments`:
  Emit Event: `ASSESSMENT_MISSING_URGENT`
- IF the moving average of the last 3 `completed_assessments` in a subject shows a > 15% drop compared to the previous 3:
  Emit Event: `ASSESSMENT_TREND_DECLINING`

## 4. Unified Obligation Stream (Task Engine)

ASPIRE merges all student tasks into a single prioritized stream.

### 4.1 Task Sources
Tasks can be generated by:
1. **Academic Calendar** (e.g., "Pay semester fee", "Fill exam form")
2. **Subject Assessment** (e.g., "Submit DBMS Lab Record")
3. **AI Intervention Plan** (e.g., "Attend next 2 DBMS classes")
4. **Mentor Request** (e.g., "Schedule 1:1 meeting with mentor")

### 4.2 Task Schema
Every task must contain:
- `id`: UUID
- `student_id`: UUID
- `source_type`: ENUM (CALENDAR, ASSESSMENT, AI_PLAN, MENTOR)
- `title`: String
- `deadline`: Timestamp (Nullable)
- `status`: ENUM (PENDING, COMPLETED, OVERDUE, SNOOZED)
- `urgency_score`: Integer (0-100, calculated by priority engine)

### 4.3 Task Priority Engine
Sorts tasks for the student UI.
**Rules:**
1. OVERDUE tasks are always pinned to the top.
2. If `deadline - now < urgency_windows.assignment_due_days`, score = 90.
3. AI_PLAN tasks have a default score of 70.
4. CALENDAR tasks with no deadline have a default score of 30.

## 5. Mentor Priority Queue Engine

Mentors do not see an alphabetical list of students. They see a priority queue of open intervention cases.

### 5.1 Urgency Bands
Every open case is assigned an urgency band by the deterministic engine:
- **URGENT:** Triggered by `ATTENDANCE_RISK_CRITICAL` OR (any risk + Exam is within `exam_approaching_days`).
- **ATTENTION:** Triggered by `ATTENDANCE_RISK_WARNING` OR `ASSESSMENT_MISSING_URGENT`.
- **MONITOR:** Mentor manually assigned "Snooze/Monitor", or it is a routine check-in.

### 5.2 Queue Sorting
Within the same urgency band, cases are sorted by:
1. `Days since last mentor action` (Descending - oldest untouched cases first)
2. `Data freshness` (Ascending - most recently updated facts first)

## 6. Learning Workspace (RAG Module)

This is the evolution of the existing EduGen capabilities.

### 6.1 Document Ingestion
- Uploaded PDFs/Docs are chunked and vectorized using `BGE-M3` (or configured embedding model).
- Embeddings are stored in PostgreSQL via `pgvector`.
- Metadata (subject, student_id, topic_tags) is strictly enforced for RBAC filtering.

### 6.2 Quiz Generation (Contract)
The AI Agent generates quizzes, but it must obey this contract:
- **Input:** `student_id`, `subject`, `topic`, `num_questions`
- **Constraint:** The LLM prompt MUST include the retrieved chunks from the student's own uploaded documents.
- **Output:** Structured JSON containing the questions, options, correct answer, and the *exact source chunk* that proves the answer.
- **Rule:** If the retriever returns no chunks for the topic, the quiz generation MUST fail gracefully, not hallucinate general knowledge.
